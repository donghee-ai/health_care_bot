# 성능 실측 · 로드맵

본 문서는 "왜 11 FPS인가"에 대한 실측 근거와, 올릴 수 있는 방법을 효과 순으로 정리합니다.
그리고 지금 남아 있는 할 일의 우선순위를 담습니다. 추측을 배제하고 **측정된 것만** 적습니다.

## 0. 한 눈에

| 항목 | 실측 | 측정 시점 |
|---|---|---|
| e2e FPS | **11.3~11.4** | 2026-07-21 |
| 루프 지연 `loop_ms` | ~90 ms | |
| CPU 사용률 (4코어 합산 100% 기준) | **~83%** (`vmstat` 교차검증 84%) | 2026-07-19 |
| CPU 클럭 | 4코어 전부 **2016 MHz = 최대** | schedutil이 이미 최대까지 밀어붙임 |
| CPU 명령셋 | `asimd`만, **`asimddp`(INT8 dotprod) 없음** | |
| RSS | ~215 MB | |
| SoC 온도 | 51°C(경부하) ~ 73°C(추론 지속) | throttle 전 |
| dropped_frames | 0 | |

**결론: 시스템은 invoke(추론) 바운드다.** 모델을 안 바꾸면 유일한 큰 레버는 NPU 델리게이트다.

## 1. 왜 FPS가 안 오르나

### 1-1. 실험과 결과

| 실험 | 결과 |
|---|---|
| 인코딩 ON(`--serve 8080`) vs OFF(`--serve 0`) | 11.34 ↔ 11.41 FPS = **차이 ~0** (오차 범위) |
| 카메라 15 fps 캡 시도 | 카메라가 무시(actual 30.5 유지) → 비교 불가 |
| CPU 거버너 | 이미 최대 클럭 → 여지 없음 |

### 1-2. 왜 화면을 꺼도 안 오르나

루프가 `grab → invoke → draw → encode` **직렬**이고, 구간마다 코어 사용이 다르다:

```
invoke 구간        : 4코어 100%  ← 여기가 대부분의 시간
draw/encode 구간   : 1코어만 (3코어 유휴)
                     → 평균 CPU가 ~85%로 보이는 이유
```

화면/인코딩을 끄면 사라지는 것은 "3코어가 노는 짧은 꼬리"다. **invoke가 쓸 수 있는 코어를
늘려주지 못하므로** FPS가 안 오른다. 병목은 invoke 지연 그 자체이고, 남는 15%는 invoke가 쓸
수 없는 단일스레드 유휴다.

## 2. 올리는 방법 (효과 순)

| # | 방법 | 기대 | 상태 |
|---|---|---|---|
| 1 | **NPU/DSP 델리게이트** (Qualcomm Hexagon HTP · QNN/LiteRT) | **큼** — INT8 전용 하드웨어로 오프로드하면 CPU도 풀린다 | **미착수 (최우선)** |
| 2 | Adreno GPU 델리게이트 | 애매 — GPU는 FP16 선호, INT8엔 불리 | 미검토 |
| 3 | 클럭/거버너 | 없음 — 이미 최대 | 확인 완료 |
| 4 | 발열 관리 | 부스트 아님 — soak에서 클럭 유지용 | — |
| 5 | 스레드/파이프라인 (draw·encode를 다음 invoke와 겹침) | 소폭 ~10%, 복잡도↑ | 미착수 |
| — | 모델 교체 (Thunder → Lightning) | 큼 | **사용자 지시로 제외** |

### 2-1. NPU 델리게이트 — 착수 지점

CPU에 `asimddp`가 없어 INT8 고속 커널을 못 쓰는 상황이므로, INT8 전용 하드웨어로 넘기는 것이
정공법이다. 다음 세션에서 확인할 것:

1. 디바이스에 **Hexagon/QNN 라이브러리가 있는지** (`libQnn*` 계열 탐색)
2. `ai_edge_litert`의 **델리게이트 API**로 붙일 수 있는지
3. **AI Hub QNN 컴파일 모델이 필요한지** (현재 TFLite INT8을 그대로 쓸 수 있는지)

정확도를 버리지 않고 FPS를 올리는 유일한 경로라 우선순위가 가장 높다.

## 3. `--idle-skip-draw` — 검증된 소폭 이득

**스트림 뷰어가 0명일 때** draw+encode를 통째로 건너뛰는 opt-in 플래그.

| 모드 | FPS |
|---|---|
| 비게이팅 (기본) | ~11.34 |
| 게이팅 (뷰어 0명, 인코딩 skip) | **~11.44** (11.2~11.6, 변동 감소) |

**이득 ~0.1~0.3 fps + 안정화** — 예측한 "소폭"과 일치한다. 천장 ~11.4는 invoke 바운드 그대로다.
정확도 손해 0이고, 플래그가 없으면 기존과 100% 동일하게 항상 그린다.

> 이 결과로, "스트리밍 온/오프 게이팅으로 성능을 얻는다"는 방향은 **실익이 ~0으로 확인**됐다.
> 관련해 승인받아 뒀던 별도 계획은 사실상 폐기 권고 상태다.

## 4. CPU · 발열 여유

**측정 시점 CPU 83%** — 추론(MoveNet Thunder INT8, 11 FPS, 4스레드)과 MJPEG 인코딩이 대부분을
쓰고 있고 **이미 warning 구간(70~90%)이다.** 앞으로 기능을 얹을 때 반드시 참고할 수치다:

- FPS를 올리려는 시도는 CPU 여유가 없어 한계가 있다.
- MCU 트랙(보류)이나 KWS 같은 추가 워크로드를 얹으면 **이 17%를 나눠 써야 한다.**
- 온도는 추론 지속 시 73°C까지 올라간다(throttle 전). **soak(장시간) 측정은 아직 안 했다.**

> `cpu_percent`는 컨테이너 안에서도 **호스트 전체 부하**다(procfs 네임스페이스 미분리).
> 이 프로세스만의 사용률이 아니다 — [`02`](02_http_api_and_stats.md) §4.

## 5. 다음 할 일 우선순위

### 5-1. 실측이 필요한 것 (코드 작업 아님, 최우선)

1. **운동 3종을 실제 사람으로 카운팅 검증 + 임계 튜닝** — 현재 값은 합리적 기본값일 뿐이다.
   누락/중복을 보고 조정한다. 스쿼트는 **발목까지 프레임에 들어오는 거리**에서 해야 각도가
   나온다. 레터럴은 팔꿈치를 곧게, 정면 응시.
2. **PTZ 상체 프레이밍 실측** — 숄더프레스/레터럴에서 머리 위 팔이 프레임에 남는지. 잘리면
   `ptz_controller.py::pitch_target_y_upper`를 0.64 → 0.68~0.72로.
3. **스쿼트 회귀 확인** — 종목 개편·추적 분리 이후에도 종전과 동일하게 추적·카운트되는지.
4. **검출 안정성** — `ptz=lost`가 8초 연속 나온 구간의 원인(거리/화각/조명)을 `/app` 프레이밍
   화면으로 좁힌다.

## 6. 보류 / 기각된 방향

| 항목 | 판단 |
|---|---|
| 모델 교체 (Thunder → Lightning) | **사용자 지시로 제외** |
| 스트리밍 게이팅으로 성능 확보 | 실측 이득 ~0 → 사실상 폐기 (§3) |
| MCU 듀얼브레인 트랙 | Linux↔MCU가 Router Bridge RPC뿐이고 서보 배선 불가 → **잠정 보류** |
| 관성 등속 전환 | overshoot·FPS 의존 증가, 급정거 → 기각 |
| 해부학 범위/좌우 불일치 게이트 | 검출률만 떨어뜨리고 근본 원인 못 잡음 → 기각 |

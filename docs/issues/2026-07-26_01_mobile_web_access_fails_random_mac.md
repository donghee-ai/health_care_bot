# 폰으로 로봇 웹앱 접속 안 됨 — 폰 "랜덤 MAC"이 원인 (ERR_ADDRESS_UNREACHABLE)

## 증상

사용자 폰에서 `http://192.168.0.45:8080/app` 접속 시 크롬 에러:

```
사이트에 연결할 수 없음
http://192.168.0.45:8080/app 에 연결할 수 없습니다.
ERR_ADDRESS_UNREACHABLE
```

- **다른 사람 폰은 같은 네트워크면 정상 접속**된다. 사용자 폰만 안 됨.
- 같은 날 오전(11:00경)에는 **이 폰도 됐었다**(`/tmp/demo_http.log`의 `192.168.0.44` 200 기록 확인). 도중부터 안 됨.
- 폰 Wi-Fi 설정상 IP는 `192.168.0.44`로 보였다(디바이스는 `192.168.0.45`, 같은 /24).

## 원인

**폰의 "임의(랜덤)/비공개 Wi-Fi MAC 주소" 기능.** 랜덤 MAC이 켜져 있으면 공유기가 그 폰을 매번 다른 기기로 인식해 **다른 서브넷 배정 또는 격리** 처리를 하고, 그 결과 폰이 `192.168.0.0/24`로 가는 **경로 자체를 잃는다.**

**에러 메시지가 핵심 단서였다:**

| 크롬 에러 | 의미 | 원인 방향 |
|---|---|---|
| **`ERR_ADDRESS_UNREACHABLE`** | 대상 IP로 가는 **경로 없음** | 폰이 그 서브넷 밖(랜덤MAC / 셀룰러 폴백 / 다른 SSID) |
| `ERR_CONNECTION_TIMED_OUT` | 경로는 있는데 응답 없음 | AP 클라이언트 격리 / 방화벽 |
| `ERR_CONNECTION_REFUSED` | 닿았는데 포트 닫힘 | 서버 미기동 / 포트 오류 |

즉 `ADDRESS_UNREACHABLE`는 **서버·네트워크 문제가 아니라 폰이 해당 LAN에 실제로 안 붙어 있다**는 신호다.

## 진단 과정 (오인 방지)

디바이스·네트워크는 정상임을 먼저 배제했다:

- `:8080`(run.sh)·`:8777`(정적) 둘 다 `ss -tlnH`에서 `0.0.0.0` 바인딩 확인.
- **AP 클라이언트 격리 아님** — PC의 Wi-Fi 인터페이스(`192.168.0.9`)에서 소스 바인딩해 `192.168.0.45:8080/8777`로 TCP 접속 성공(무선→무선 통함).
- 접속 로그(`/tmp/demo_http.log`)에 폰 요청이 **도달했는지** 확인 → 특정 시점 이후 도달 안 함(경로 소실과 일치).

## 영향

- 데모 중 **특정 폰만 접속 불가** → "네트워크 죽었나 / 서버 문제인가"로 오인해 엉뚱한 곳(서버·포트·코드)을 헤매게 된다. 실제로 이번에도 웹 버전 롤백까지 시도했으나 원인은 폰이었다.

## 해결

폰의 그 Wi-Fi 네트워크 설정에서 **"비공개/임의 MAC 주소" → "기기(디바이스) MAC 사용"** 으로 바꾸고 재접속 → 정상 서브넷에 붙어 즉시 해결.

## 재발 방지

- **에러 메시지로 먼저 원인을 가른다** (위 표). `ADDRESS_UNREACHABLE`면 서버가 아니라 **폰의 네트워크 소속**부터 본다.
- 폰 쪽 진단 순서: ① 모바일 데이터 OFF(로봇 Wi-Fi에 인터넷 없으면 LTE로 새어나감) → ② 다른 폰과 **정확히 같은 SSID**(…5G/guest/중계기 아님) → ③ 폰 IP `192.168.0.x` 확인 → ④ Wi-Fi 잊기·재접속("인터넷 없음, 연결 유지?"→유지) → ⑤ **랜덤 MAC OFF** → ⑥ VPN/사설DNS OFF.
- **데모 당일**: 참석자 폰들도 같은 함정 가능 → 접속 안 되는 폰은 "그 네트워크에서 랜덤 MAC 끄기"를 먼저 안내. 가능하면 공유기 쪽에서 랜덤MAC 클라이언트를 정상 서브넷에 넣도록 설정.

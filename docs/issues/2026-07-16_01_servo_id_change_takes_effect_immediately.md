# ST3215 ID 변경이 "실패" 로그를 남기고도 실제로는 즉시 반영됨

## 증상

`set-id` 명령(`unlock LOCK → write ID → lock LOCK`, 모두 기존 ID로
전송)을 실행했더니 `[FAIL] 응답 헤더 없음/깨짐: b''` 에러로 실패
처리됐다. 그런데 그 이후 같은 ID로 재시도(`ping`)해도 계속 응답이
없었고, 새 ID로 `ping`을 날려보니 **정상 응답**이 왔다 — 즉 명령은
"실패"로 보고됐지만 ID 변경 자체는 이미 성공한 상태였다.

## 원인

일부 Feetech 레퍼런스(예: 서드파티 Python SDK의 `set_motor_id` 경고
문구, "전원 재투입 후 반영됨")는 ID 변경이 **전원 재투입 전까지는
적용되지 않는다**고 가정하고, unlock/write/lock 세 패킷을 전부
**기존 ID**로 보내도록 짜여 있다. 하지만 이번에 쓴 실제 서보 펌웨어는
`ID` 레지스터(addr 5)에 새 값을 쓰는 즉시 자신의 통신 ID를 전환한다.
그 결과:

1. `write_byte(old_id, ADDR_ID, new_id)` 패킷을 받는 순간 서보가
   이미 `new_id`로 전환됨.
2. 바로 다음에 보낸 `write_byte(old_id, ADDR_LOCK, 1)`(lock) 패킷은
   이제 아무도 응답하지 않는 `old_id`로 전송된 것이 되어 타임아웃 →
   `b''` 빈 응답 → 스크립트가 실패로 보고.
3. 그러나 ID 전환 자체(1~2단계)는 이미 끝난 뒤였으므로, 실제로는
   EEPROM 쓰기가 (lock 재설정만 빠진 채) 성공한 상태.

## 해결

새 ID로 재시도 `ping`을 날려서 이미 전환됐는지부터 확인하는 방식으로
대응 — 실제로 `--id 2 ping`이 정상 응답해서 변경이 이미 끝났음을
확인했다. `set-id` 서브커맨드 자체는 코드 수정 없이 그대로 둠 (lock
스텝이 새 ID로 실패하는 것 자체는 무해 — EEPROM 잠금이 안 걸린
상태로 남을 뿐, 다음 세션에서 `unlock`부터 다시 하면 잠글 수 있음).

## 재발 방지

- ST3215(적어도 이번에 쓴 개체/펌웨어 버전)는 **ID 변경이 즉시
  반영**된다 — "전원 재투입 필요"라는 일반적인 SDK 경고 문구를
  맹신하지 말 것. `set-id` 실행 후 실패 로그가 떠도 곧바로 새 ID로
  `ping`해서 실제 상태부터 확인한다.
- 여러 서보를 동시에 체인에 물린 채로 ID 변경을 시도하면, 위 즉시전환
  특성 때문에 ID 충돌/응답 없음이 더 헷갈리게 나타날 수 있다 — 반드시
  서보를 **한 번에 하나씩만** 어댑터에 연결한 상태에서 ID를 미리
  나눠 기록한다(`ptz/sketch/health_care_ptz.ino` 헤더 주석과 동일한
  권고).
- `set-id` 명령의 마지막 `lock` 스텝이 실패로 뜨는 것은 사실상
  "ID가 이미 바뀌어서 옛 주소가 응답 안 하는" 정상적 부작용이지,
  EEPROM 쓰기 자체의 실패를 의미하지 않는다.

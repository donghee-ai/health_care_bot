# 2026-07-19 — PTZ 제어를 시간 기준으로 전환 + 추적 손실 복구 사다리

## 시점

2026-07-19. UNO Q 실기에서 PTZ 추적을 처음 돌려본 직후
([`2026-07-19_01`](2026-07-19_01_device_code_deploy_synced.md)에서 코드 동기화 완료).

## 사건

실기에서 카메라가 "톡톡" 끊기며 따라오는 현상. 원인이 제어 법칙의 프레임
의존성으로 밝혀져 **각속도(deg/s) 기준으로 전환**하고, 명령 주기와 손실
복구 동작까지 함께 정리.

## 배경 — 왜 PC에선 부드럽고 실기에선 끊겼나

코드는 PC와 디바이스가 md5까지 동일했다. 차이는 **프레임레이트**였다.

| | FPS | 출처 |
|---|---|---|
| 개발 PC | ~29 | [`2026-07-17_03`](2026-07-17_03_ptz_camera_tracking_v1_local_pc.md) |
| UNO Q | ~11 | 이번 실기 로그 실측 |

기존 제어식은 `step = clamp(gain * ex, ±max_step) * scale`을 **매 프레임
누적**했다. 즉 `gain=8.0`, `max_step=4.0`은 "프레임당 도수"였고, 암묵적으로
29 FPS에 튜닝된 값이었다. 11 FPS에서는 같은 시간에 누적되는 프레임이
1/2.6로 줄어 **각속도도 1/2.6**이 됐다.

여기에 두 번째 요인이 겹쳤다. 서보는 569 tick/s ÷ 11.375 tick/deg =
**50 deg/s**로 도는데, 목표각이 밀리는 속도는 최대 29 deg/s였다. **서보가
목표보다 1.7배 빠르니 매번 먼저 도착해서 남는 시간을 멈춰 있었다.**
250ms 주기 기준으로 오차가 클 때도 105ms(주기의 42%), 절반일 땐 178ms(71%)를
정지 상태로 보냈다. 이게 "톡톡"의 정체.

## 변경 1 — 프레임당 → 초당 (각속도)

`ref_fps`를 곱하는 중간 단계를 거쳐 최종적으로 **deg/s를 직접 표현**하도록
정리했다. 제어식에서 프레임레이트 개념이 완전히 사라졌다.

```python
# 전 - "29 FPS에서의 프레임당 도수"라는 간접 단위
gain: float = 8.0
max_step: float = 4.0

# 후 - 각속도 그 자체
gain_deg_per_s: float = 232.0    # 8.0 x 29
max_deg_per_s: float = 116.0     # 4.0 x 29
```

```python
deg_per_s = clamp(gain_deg_per_s * ex, ±max_deg_per_s) * scale
self.pan_deg += yaw_sign * deg_per_s * dt_s
```

`dt_s`는 `max_dt_s=0.15`로 상한을 둔다 — LOST 구간을 건너뛴 직후 dt가 커져
한 번에 튀는 것을 막기 위함. 첫 프레임은 간격을 알 수 없으므로 `dt_s=0`.

**검증** (합성 keypoint, 1초간 yaw 회전량):

| FPS | BEFORE | AFTER | 29 FPS 대비 편차 |
|---|---|---|---|
| 29 (PC) | 25.20 | 25.20 | 0% — 회귀 없음 |
| 20 | 17.10 | 24.79 | 32% -> 1.6% |
| **11 (UNO Q)** | **9.00** | **23.73** | **64% -> 5.8%** |
| 6 | 4.50 | 19.57 | 82% -> 22.3% |

6 FPS의 잔여 편차는 `max_dt_s` 상한이 걸린 것으로 의도된 동작.

## 변경 2 — 명령 쿨다운 250ms -> 80ms

서보가 먼저 도착해 노는 문제를 직접 해소. 11 FPS면 프레임 간격이 91ms라
80ms는 사실상 "매 프레임 전송"이 된다. 1Mbaud에 명령 15바이트라 버스 부하는
무시 가능.

**사용자 체감으로 개선 확인됨** ("아까보다 낫다") — 서보가 먼저 도착해
정지한다는 진단이 맞았음.

## 변경 3 — 추적 손실 복구 사다리 (yaw 전용)

기존에는 미검출이면 `return None`으로 **아무것도 안 했다.** 사람이 빠르게
프레임 밖으로 나가면 카메라가 그 자리에 얼어붙었다.

4단계 사다리를 넣었다. 어느 단계든 **재검출되면 즉시 취소**되고 정상 추적
으로 돌아간다.

```
연속 미검출 3프레임 (단발 깜빡임 무시)
  -> 관성 10프레임 (마지막 yaw 각속도로, 프레임당 0.8 감쇠)
  -> 그 자리에서 1초 대기
  -> 관성 이전 위치로 복귀, 2초 대기
  -> 중앙(180) 복귀 후 정지
```

**관성 방향은 "마지막 yaw 각속도"를 쓴다.** 이게 핵심 안전장치다 — 사람이
중앙에 가만히 있어 카메라가 안 움직이던 중이면 각속도가 0이라 **관성이 아예
안 걸린다.** 검출만 깜빡인 경우의 헛발질이 이 규칙 하나로 걸러진다.

**검증** (11 FPS 시뮬레이션, 서보 없이):

| 시나리오 | 결과 |
|---|---|
| 깜빡임 필터 | miss 1~2 무반응 |
| 관성 | miss 3~12, 총 +10.6도 (감쇠 적용) |
| 1초 후 복귀 | miss 23에서 `BACK` — 관성 이전 위치와 정확히 일치 |
| 2초 후 중앙 | miss 45에서 `CENTER 180.0` |
| 소프트리밋 | 90 <= 180 <= 270 준수 |
| 관성 중 재검출 | stage 즉시 `none`, 상태 전부 초기화 |
| **정지 중 손실** | 각속도 0 -> **관성 0.00도**, 바로 대기 단계로 |

로그 태그: `COAST` / `BACK` / `CENTER`.

## 변경 4 — 관성 근거를 "피사체 속도"로 교체 (실기 피드백 반영)

복구 사다리를 실기에서 돌려본 결과, **빠르게 프레임을 벗어나면 관성이 아예
걸리지 않는** 문제가 보고됐다. 적당한 속도로 나가면 정상 동작.

### 원인 — 데드존 밴드

초기 구현은 관성 방향/속도를 **카메라의 마지막 각속도**(`_last_yaw_vel`)에서
가져왔다. 그런데 이 값은 `yaw_out`일 때만 갱신된다:

```python
yaw_dead = 0.5 - sector_side = 1/3        # 중앙 4/6 밴드
yaw_out = abs(ex) > yaw_dead              # 밴드 밖일 때만 카메라가 움직임
```

**중앙 밴드 안에서는 카메라가 안 움직이므로 각속도가 0이다.** 빠르게 나가면
그 밴드를 한 프레임도 밟지 않고 화면 밖으로 사라질 수 있다 — 11 FPS면 프레임
간격이 91ms라 2~3프레임 만에 중앙에서 화면 밖까지 간다.

시뮬레이션으로 재현 확인:

| 시나리오 | 손실 직전 카메라 각속도 | 관성 |
|---|---|---|
| 느린 이탈 (밴드 밖 체류) | +22.48 deg/s | O |
| **빠른 이탈 (밴드 안에서 사라짐)** | **+0.00** | **X** |
| 빠른 이탈 (밴드 밖 1프레임만) | +11.14 | O (절반) |

사용자가 후보로 지목한 "3프레임 필터"나 "중앙에서 사라졌다는 판정"이 아니라
**데드존 밴드가 원인**이었다.

### 설계 결함 — 카메라 속도는 잘못된 신호였다

"카메라가 얼마나 돌고 있었나"는 "사람이 얼마나 빨리 움직였나"가 아니다.
반대 경우도 문제다 — 카메라가 사람을 잘 따라가고 있으면 화면 속 사람은 거의
정지해 보이므로, 그 상태로 이탈해도 신호가 약하다.

올바른 값은 **사람의 실제 각속도**이고, 두 성분의 합이다:

```
사람의 각속도 = 카메라 각속도 + (화면 내 잔여 이동량 x 화각)
```

`_prev_smooth_x`를 들고 프레임 간 변화량으로 화면 내 피사체 속도를 낸다.
손실 구간을 건너뛴 델타는 시간 간격이 불확실해 버린다.

### 결과

| 시나리오 | 카메라 | 화면 내 | 관성 초기속도 |
|---|---|---|---|
| 느린 이탈 | +22.48 | +0.53/s | +43.47 deg/s |
| **빠른 이탈 (중앙에서)** | 0 | +1.02/s | **+49.00** |
| 초고속 (1프레임) | 0 | +1.32/s | **+63.36** |
| **중앙 정지 손실** | 0 | 0 | **0** (관성 안 걸림) |
| 가장자리 정지 손실 | +23.19 | 0 | +18.62 |

**이탈이 빠를수록 관성이 커진다.** 그리고 제자리 손실에서 관성이 안 걸리는
안전 성질은 그대로 유지됐다 — 두 성분이 모두 0이기 때문.

소프트리밋도 한계에서 밀어붙여 검증했다. yaw 90~270을 넘지 않고(정확히
270.00 / 90.00에서 정지), 관성 속도도 `max_deg_per_s=116`에서 잘린다.
pitch는 복구 사다리가 건드리지 않는다(yaw 전용).

### 현재 튜닝값

| 필드 | 값 | 비고 |
|---|---|---|
| `coast_start_misses` | 3 | 0.27초는 깜빡임으로 무시 |
| `coast_frames` | 15 | 11 FPS에서 1.36초 |
| `coast_decay` | 0.9 | 약 44도 이동 |
| `coast_fov_deg` | 60 | **추정값 — 실측 보정 필요** |

`coast_fov_deg`는 카메라 수평 화각으로, 관성 속도를 직접 결정한다. 정확한
값을 모르므로 60도로 두었다. 보정법: 카메라를 알려진 각도만큼 돌려놓고
피사체가 화면 폭의 몇 %만큼 밀리는지 재면 나온다 (15도 회전에 30% 밀리면
화각 = 15 / 0.30 = 50도).

**로봇에서 동작 확인됨 — 잘 따라간다.** 위 튜닝값(`coast_frames=15`,

특히 최초 보고였던 **"빠르게 나가면 못 따라온다"가 해소된 것을 확인**했다.
`coast_fov_deg=60`은 여전히 실측이 아닌 추정값이지만 실기에서 충분히 동작하므로,
정밀 보정은 필요해지는 시점으로 미룬다.

## 발견했으나 고치지 않은 것

### 스쿼트 rep 오검출 — `bottom=5도`

첫 실기 스쿼트 측정에서 가짜 rep이 잡혔다.

```
[ 180] L=119 R=180도     <- 좌우 61도 차이. 이미 신뢰 못 할 값
[ 195] L=  ? R=  ?도     <- 검출 실패
[ 210] L=  ? R=  ?도     <- 검출 실패
  * SQUAT REP #1  bottom=5도  (frame 216)
[ 225] L=173 R=175도
```

무릎 각도 5도는 해부학적으로 불가능(실제 한계 30~40도). 원인은 **2D 투영
왜곡** — 다리가 카메라 쪽을 향하면 hip-knee-ankle이 화면상 거의 한 점으로
뭉쳐 각도가 실제보다 훨씬 작게 나온다. 키포인트 오류가 아니라 정상
키포인트의 투영 문제라, `conf >= 0.3` 게이트로는 걸러지지 않는다.

구조적 취약점도 확인: **rep 하나가 단 2개의 유효 샘플로 완성된다.**
`None` 프레임은 상태를 유지한 채 그냥 넘어가므로, 검출이 끊긴 구간을 사이에
두고 "튄 값 1개 + 정상값 1개"만으로 UP->DOWN->UP이 성립한다. `min_dwell_ms=200`은
11 FPS에서 3프레임이면 넘어 제약이 못 된다.

**대응 보류 결정.** 검토한 방안과 기각 사유:

- *해부학적 범위 게이트(30도 미만 버리기)* — 왜곡은 자세에 따라 연속적으로
  생기므로 30도를 잘라도 31도짜리 왜곡값은 통과한다. 증상의 꼬리만 자름
- *좌우 40도 불일치 게이트* — 양쪽이 동시에 잡혀야 비교가 되는데 한쪽만
  잡히는 프레임이 많아, 정작 필요한 상황에 작동하지 않음

두 방안 모두 **검출률을 떨어뜨리면서 근본 원인은 못 잡는다**고 판단. 이미
`?`가 대부분인 상황에서 더 조이면 카운트 자체가 불가능해진다. 사용자 판단으로
현행 유지.

향후 검토할 대안: `DOWN` 구간에 **유효 샘플 N개 이상**을 요구 (검출률을
건드리지 않고 2샘플 rep만 차단), 또는 측면 촬영 전제, 또는 각도 대신 투영에
덜 민감한 지표(엉덩이 높이 변화량 등).

### 관성 지속 시간이 아직 "프레임 수" 기준 (의도적 보류)

추적 제어는 시간(deg/s) 기준으로 바꿨는데, **관성 지속만 `coast_frames`라는
프레임 수로 남아 있다.** 같은 실수를 한 군데에 다시 넣은 셈이다.

결과적으로 FPS가 다르면 관성 지속 시간과 이동 거리가 달라진다:

| | 프레임 간격 | 15프레임 지속시간 | 상대 이동거리 |
|---|---|---|---|
| UNO Q (11 FPS) | 91ms | 1.36초 | 1.00 |
| PC (29 FPS) | 34ms | 0.52초 | 0.38 |

**PC에서 디버깅하면 관성이 2.6배 짧게 보인다.** 지금은 UNO Q에서만 돌리므로
실사용에는 영향이 없어 보류했으나, PC와 실기 동작을 비교할 때 혼동의 원인이
될 수 있다.

고치려면 `coast_frames: int` -> `coast_duration_s: float`로 바꾸고, 감쇠도
프레임당이 아니라 시간당(`decay^(dt/기준dt)`)으로 환산해야 한다.

### 감쇠가 지배적이라 coast_frames는 거의 효과가 없다

관련해서 측정으로 드러난 것. `coast_decay=0.8`이면 프레임을 늘려도 이동
거리가 거의 안 늘어난다 — 뒤쪽 프레임의 속도가 이미 0에 가깝기 때문.

| coast_frames | 이동거리 | | coast_decay | 이동거리 |
|---|---|---|---|---|
| 10 | 24.85도 | | 0.80 | 26.86도 |
| 15 | 26.86도 (+8%) | | 0.85 | 33.88도 (+26%) |
| 30 | 27.81도 (+12%) | | 0.90 | 44.22도 (+65%) |

**관성 거리를 조절하려면 `coast_frames`가 아니라 `coast_decay`를 만져야 한다.**
`coast_frames`는 "얼마나 오래 꼬리를 끄는가"만 결정한다.

### 검출 불안정 — 실질적 병목

로그에 `ptz=lost`가 **90프레임(약 8초) 연속**으로 나오는 구간이 있었다. 사람이
그 자리에 있는데 못 잡은 것. 무릎 각도도 대부분 `?`(hip/knee/ankle 3점 중
하나 이상이 conf 미달). **스쿼트 검증의 실질적 병목은 제어가 아니라 검출**이다.
거리/화각/조명 중 무엇이 원인인지는 `/app` 화면으로 프레이밍을 봐야 갈린다.

## 문서 오류 — 아직 미수정

이번 실기에서 기존 문서 두 곳이 틀렸음이 드러났다. **아직 안 고쳤다.**

1. **"Venus가 video0·1을 선점하니 video2 이상이 진짜 카메라"** — 이번 부팅에선
   **정반대**였다. USB 카메라가 `/dev/video0`·`video1`, Venus가 `video2`·`video3`.
   즉 노드 번호는 부팅마다 바뀌므로 **매번 `v4l2-ctl --list-devices`로 확인**해야
   하고, "video2 이상"이라는 규칙 자체가 틀렸다.
   (HANDOFF §5-2, `docker/run.sh` 주석)
2. **`SERIAL_DEV` 기본값 `/dev/ttyUSB0`** — 실제로는 CH343이 **`/dev/ttyACM0`**로

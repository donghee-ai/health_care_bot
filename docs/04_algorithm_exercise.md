# 운동 인식 · rep 카운팅 알고리즘

본 문서는 스쿼트 / 숄더프레스 / 사이드 레터럴 레이즈가 **어떻게 감지·카운트되는지**와,
왜 이 종목들을 골랐는지, 그리고 현재 알려진 실패 모드를 정리합니다. 임계값을 만지기 전에
상태기계 동작 모델을 정확히 알도록 작성합니다.

구현: [`src/exercise_counter.py`](../src/exercise_counter.py) ·
[`src/angles.py`](../src/angles.py)
종목별 카메라 프레이밍은 [`03_algorithm_ptz_tracking.md`](03_algorithm_ptz_tracking.md).

## 0. 한 눈에 — 4단계 흐름

```
[1] MoveNet Thunder INT8 출력
    [1, 1, 17, 3]   ← 17 keypoint × (y_norm, x_norm, confidence)
         ↓
[2] 관절 각도 계산 (좌/우 각각)
    squat            : knee_angle(hip-knee-ankle)
    overhead/lateral : shoulder_elev_angle(elbow-shoulder-hip)
         ↓  conf 미달이면 None
[3] 좌/우 → 대표 각도 1개
    pick_angle(L, R, mode="better")
         ↓
[4] 상태 머신 (RepCounter)
    UP ↔ DOWN  /  한 사이클 = 1 rep   (히스테리시스 + dwell)
```

세 종목이 **같은 상태기계 하나**를 쓴다. 종목마다 다른 것은 "어떤 각도"와 "임계값"뿐이다.

## 1. 핵심 전제 — 2D 포즈는 이미지 평면 안의 각도만 정확하다

관절이 카메라 앞뒤(depth) 방향으로 움직이면 그 각도는 화면상에서 뭉개진다. 그래서 이 봇의
종목은 전부 **정면을 보고 서서, 팔·다리가 화면 평면 안에서 움직이는** 것으로 골랐다.

이 전제가 종목 선정(§7)과 실패 모드(§6)를 동시에 설명한다.

## 2. 각도 계산

```python
angle_3pt(a, b, c):                 # 중심 b, 2D 점 (y, x)
    cos = dot(a-b, c-b) / (|a-b| * |c-b| + 1e-9)
    return degrees(arccos(clip(cos, -1, 1)))     # ← 정의역 보호
```

**세 점 중 하나라도 `conf < conf_th(0.3)`면 `None`을 반환한다.** 낮은 신뢰도의 좌표가
각도에 섞여 NaN처럼 전파되는 것을 입구에서 막는다.

### 2-1. 종목별 각도 정의

| 종목 | 함수 | 3점 (중심이 가운데) |
|---|---|---|
| 스쿼트 | `knee_angle` | hip – **knee** – ankle |
| 숄더프레스 | `shoulder_elev_angle` | elbow – **shoulder** – hip |
| 레터럴 | `shoulder_elev_angle` | elbow – **shoulder** – hip (같은 각도) |

> **무릎 각도는 hip·knee·ankle 3점이 모두 보여야 나온다** → 발목까지 프레임에 들어오는
> 거리에서만 스쿼트가 카운트된다. 실기에서 각도가 `?`로 찍히는 주 원인이다.

### 2-2. 좌/우 통합 — `pick_angle`

```
better(기본) : 둘 다 있으면 평균, 한쪽만 있으면 그쪽
avg          : 둘 다 있을 때만 평균 (한쪽만이면 None)
left / right : 강제 선택
```

한쪽 관절이 계속 튀면 `--side left`/`right`로 고정할 수 있다.

## 3. 공통 엔진 — `RepCounter`

```
        angle < down_th  AND  경과시간 >= min_dwell_ms
   UP ─────────────────────────────────────────────────> DOWN
    ^                                                     │
    │        angle > up_th  AND  경과시간 >= min_dwell_ms  │
    └──────────────── reps += 1 ◄─────────────────────────┘
```

`angle_deg`가 `None`이면 **아무 일도 하지 않고 상태를 유지한 채 넘어간다** — 검출이 끊겨도
진행 중인 rep이 깨지지 않게 하려는 설계다. 이 성질이 §6-1의 취약점과 직결된다.

### 3-1. 두 가지 방어장치

- **히스테리시스** (`down_th < up_th`) — 임계를 하나만 두면 그 근처에서 각도가 미세
  진동할 때 카운트가 폭발한다. 내려가는 문턱과 올라오는 문턱을 벌려 막는다.
- **dwell** (`min_dwell_ms = 200`) — 상태 전환 직후 최소 유지 시간. keypoint 지터로 인한
  순간 떨림을 무시한다.

### 3-2. 부수 기록

| 필드 | 뜻 |
|---|---|
| `min_angle_in_down` | 지금 DOWN 구간의 최저 각도 (진행 중) |
| `last_rep_min_angle` | 직전 rep의 bottom 각도 |
| `deepest_overall` | 세션 전체 최고 기록 |

`state`·`reps`·`thresholds_deg`까지 `snapshot()`으로 `stats.json`에 실린다
([`02`](02_http_api_and_stats.md) §3).

## 4. 종목별 상세

### 4-1. 스쿼트 (하체)

| 항목 | 값 |
|---|---|
| 각도 | 무릎 = hip-knee-ankle |
| 임계 | `down < 100°` (앉음) / `up > 140°` (일어섬) |
| rep 1회 | 서있음(UP) → 앉음(DOWN) → 일어섬(UP) — **일어설 때 +1** |
| 각도 감각 | 선 자세 ≈170°, 무릎 90° 스쿼트 ≈90° |

### 4-2. 숄더프레스 / 팔 위로 올리기 (상체)

| 항목 | 값 |
|---|---|
| 각도 | 어깨 올림 = elbow-shoulder-hip |
| 임계 | `down < 60°` (팔 내림) / `up > 140°` (머리 위로 편 상태) |
| rep 1회 | 팔 내림(DOWN) → 팔 올림(UP) — **올릴 때 +1**, 내리면 다음 rep 준비 |
| 각도 감각 | 팔 내림 ≈15°, 머리 위로 곧게 ≈165° |

### 4-3. 사이드 레터럴 레이즈 (상체)

| 항목 | 값 |
|---|---|
| 각도 | 같은 어깨 올림 각도 |
| 임계 | `down < 35°` (팔 내림) / `up > 80°` (어깨 높이 수평) |
| rep 1회 | 팔 내림 → 옆으로 어깨 높이 — **올릴 때 +1** |
| 각도 감각 | 옆으로 수평 ≈90° |

> 팔꿈치를 **곧게 편 상태**여야 각도가 깔끔하다. 굽히면 팔꿈치가 몸통 쪽으로 와
> elbow-shoulder-hip 각이 왜곡될 수 있다. 또 팔이 옆으로 넓게 벌어져 좌우 프레임에 걸릴 수
> 있는데 줌이 없으므로 **사람이 더 뒤로 서는 것**이 유일한 대응이다.

### 4-4. 왜 각도 하나로 상체 두 종목을 다 세나

`elbow-shoulder-hip`(어깨를 중심으로 한 위팔–몸통 각도) 하나가 팔 높이를 전부 구분한다:

```
팔 내림 ─────────── ≈10~20°
옆으로 수평(레터럴) ─ ≈90°
머리 위로(프레스) ─── ≈160~170°
```

그래서 **각도는 공유하고 임계값만 다르게** 준다 — 숄더프레스는 머리 위(>140)까지 가야
1회, 레터럴은 어깨 높이(>80)까지만 가면 1회다.

> **상태 의미가 스쿼트와 반대다.** 상체 종목은 팔 내림 = DOWN(휴식), 팔 올림 = UP이고
> rep은 "올리는 순간" 잡힌다. 결국 한 번 올렸다 내리면 정확히 1회로 센다.

## 5. 종목 선택 — 자동분류 없음

```python
select_counter(mode, squat_c, overhead_c, lateral_c)   # mode로만 결정
```

모드는 네 가지다 — `squat` / `overhead` / `lateral` / **`guard`**. 앞의 셋만 운동이고
`guard`(경비 모드)는 **rep 카운터가 없다**(`select_counter`가 `(None, "guard")` 반환).
경비 모드의 감지·촬영 규칙은 [`02_http_api_and_stats.md`](02_http_api_and_stats.md) §1-2,
카메라 거동은 [`03`](03_algorithm_ptz_tracking.md) §9-3에 있다.

과거엔 몸 방향(세로=스쿼트 / 가로=푸시업)으로 자동 분류했지만, 지금 세 종목은 **전부
정면·직립**이라 방향으로 구분이 안 된다. 그래서:

- 종목은 **웹 UI에서 사용자가 직접 선택** → `POST /api/mode` → `app_state`에 저장.
- 추론 루프는 매 프레임 `app_state.get_mode()`를 읽어 해당 카운터를 쓴다.
- **카운터 3개는 항상 동시에 살아 있어** 모드를 바꿔도 각자 상태·횟수가 유지된다.

`angles.py::body_orientation()`은 옛 자동분류의 잔재로 지금은 `stats.json`의 표시용
필드로만 남아 있다. `elbow_angle()`도 미사용이다(무해).

### 5-1. 종목별 카메라 프레이밍 (요약)

| 모드 | 추적 목표점 | pitch 기준 | 데드존 |
|---|---|---|---|
| lower (스쿼트) | 무릎 중점 → 엉덩이 → 몸통 | 0.62 | 0.20 (넓게) |
| upper (숄더/레터럴) | **어깨 중점** → 엉덩이 → 몸통 | 0.64 | 0.15 (좁게) |
| guard (경비, 운동 아님) | 사람 중심(어깨+엉덩이 평균) | 0.50 | 0.20 |

무릎을 계속 추적하면 상체 운동에서 **머리 위 팔이 잘린다.** 그래서 상체 모드는 어깨를
추적하고 어깨를 화면 아래쪽에 둬 위쪽 공간을 남긴다. 상세:
[`03`](03_algorithm_ptz_tracking.md) §2·§4.

## 6. 알려진 실패 모드 — **스쿼트 카운팅은 아직 신뢰할 수 없다**

첫 실기 측정에서 해부학적으로 불가능한 rep이 잡혔다:

```
[ 180] L=119 R=180°     ← 좌우 61° 차이. 이미 신뢰 못 할 값
[ 195] L=  ? R=  ?°     ← 검출 실패
[ 210] L=  ? R=  ?°     ← 검출 실패
  ★ SQUAT REP #1  bottom=5°  (frame 216)      ← 무릎 5°는 불가능(실제 한계 30~40°)
[ 225] L=173 R=175°
```

### 6-1. 원인 두 가지가 겹친다

1. **2D 투영 왜곡** — 다리가 카메라 쪽을 향하면 hip-knee-ankle이 화면상 거의 한 점으로
   뭉쳐 각도가 실제보다 훨씬 작게 나온다. **키포인트 오류가 아니라 정상 키포인트의 투영
   문제**라 `conf` 게이트로는 안 걸러진다.
2. **rep 하나가 유효 샘플 단 2개로 성립한다** — `None` 프레임은 상태를 유지한 채 넘어가므로
   (§3), 검출이 끊긴 구간을 사이에 두고 "튄 값 1개 + 정상값 1개"만으로 UP→DOWN→UP이
   완성된다. `min_dwell_ms=200`은 11 FPS에서 3프레임이면 넘어 제약이 못 된다.

### 6-2. 기각한 대응과 향후 후보

**기각** (검출률을 떨어뜨리면서 근본 원인은 못 잡는다고 판단 — 이미 `?`가 대부분인 상황에서
더 조이면 카운트 자체가 불가능해진다):

- *해부학적 범위 게이트(30° 미만 버리기)* — 왜곡은 자세에 따라 연속적으로 생기므로 30°를
  잘라도 31°짜리 왜곡값은 통과한다. 증상의 꼬리만 자른다.
- *좌우 40° 불일치 게이트* — 양쪽이 동시에 잡혀야 비교가 되는데, 정작 필요한 상황이 한쪽만
  잡히는 프레임이다.

**향후 후보**: DOWN 구간에 **유효 샘플 N개 이상**을 요구(검출률을 안 건드리고 2샘플 rep만
차단), 측면 촬영 전제, 또는 각도 대신 투영에 덜 민감한 지표(엉덩이 높이 변화량 등).

### 6-3. 실질적 병목은 제어가 아니라 검출이다

로그에 `ptz=lost`가 **90프레임(약 8초) 연속**으로 나온 구간이 있었다 — 사람이 그 자리에
있는데 못 잡은 것. 무릎 각도도 대부분 `?`였다. 거리·화각·조명 중 무엇이 원인인지는 `/app`
화면으로 프레이밍을 봐야 갈린다.

## 7. 왜 푸시업을 뺐나 (2026-07-26)

2D 포즈에 부적합해서다:

- 정면/사선 푸시업은 **팔이 카메라 앞뒤(depth)로 굽어** 팔꿈치 각도가 뭉개진다.
- 옛 자동분류(가로=푸시업)가 사선/정면 자세를 오분류한다.
- 정직하게 하려면 **옆모습(side view) 고정 세팅**이 필요한데 데모에선 각도 통제가 어렵다.

→ 정면·직립 종목(숄더프레스/레터럴)으로 대체했다.

## 8. 튜닝

임계값은 **합리적 기본값**이다. 스쿼트가 그랬듯 실제 사람으로 맞춰야 한다.

| 무엇 | 어디 | 증상 → 조정 |
|---|---|---|
| 종목별 up/down 임계 | `--squat-*-th` / `--overhead-*-th` / `--lateral-*-th` | rep 누락 → 임계 간격 좁힘 / 중복 → 넓힘·dwell↑ |
| dwell | `--min-dwell-ms` (200) | 떨림으로 중복 카운트되면 ↑ |
| conf 임계 | `--conf` (0.3) | keypoint 불안정 → ↑ (단 검출률 하락) |
| 좌/우 선택 | `--side` (better) | 한쪽이 계속 튀면 `left`/`right`로 고정 |
| 상체 프레이밍 | `ptz_controller.py::pitch_target_y_upper` (0.64) | 머리 위 팔이 잘림 → 0.68~0.72 |
| 레터럴 좌우 잘림 | (코드 아님) | 줌이 없음 → **사람이 더 뒤로** |
